### **Notebook 02: Realized Volatility Construction**

**Purpose:** Implement and validate the target variable with full mathematical rigor.

**Key Operations:**

```
RV Calculation Protocol:
1. Intraday: 5-min log returns → squared → daily sum
2. Overnight: ln(Open_t / Close_{t-1})² 
3. Total: RV_t = RV_intraday + RV_overnight
4. Scaling: σ_t = √(RV_t × 10,000) for GARCH compatibility
```

**Diagnostic Checks:**

- Compare RV distribution against known stylized facts (fat tails, clustering)
- Verify scaling matches GARCH output units
- Cross-validate against external RV data sources if available

**Expected Outputs:**

| Artifact | Format |
|----------|--------|
| `realized_variance.parquet` | Parquet |
| RV time series plot | PNG |
| RV histogram with fitted distributions | PNG |
| Summary statistics table | LaTeX/Markdown |

**Explicitly Excluded:**

- Feature engineering beyond RV
- Model training

**Why This Exists:**
> The target variable is the **most critical decision** in the project. Realized volatility has multiple valid definitions (Parkinson, Garman-Klass, realized kernel, etc.). This notebook makes the choice **explicit and testable**.

**Risks Mitigated:**

- Unit inconsistency with GARCH (the ×10,000 scaling is non-obvious)
- Microstructure noise contamination (5-min sampling is a deliberate choice)
- Overnight gap handling (often ignored in naive implementations)

### **Notebook 03: Descriptive Statistics & Stylized Facts**

**Purpose:** Establish empirical baseline and verify the data exhibits expected financial time series properties.

**Key Analyses:**

| Analysis | Expected Finding | Red Flag If Not |
|----------|------------------|-----------------|
| Return distribution | Fat tails, negative skewness | Normal → data issue |
| Autocorrelation of returns | Near zero | Strong autocorr → data leakage |
| Autocorrelation of squared returns | Slow decay | No persistence → model won't help |
| Hurst exponent | ~0.5 for returns, >0.5 for volatility | Strong mean reversion in vol → different model class |
| Volatility clustering | Visual confirmation | No clustering → GARCH inappropriate |

**Expected Outputs:**

- Return distribution vs. Normal overlay
- ACF/PACF plots (returns and squared returns)
- Rolling skewness/kurtosis time series

**Why This Exists:**
> **Confirmatory analysis must follow exploration.** This notebook answers: "Does this data behave like financial data should?" If stylized facts are absent, model assumptions fail silently.

**Risks Mitigated:**

- Applying volatility models to data without volatility clustering
- Misinterpreting model "success" on non-representative data

### **Notebook 05: GARCH Benchmark**

**Purpose:** Establish a rigorous econometric benchmark that represents industry-standard practice.

**Model Specification:**

```python
arch_model(returns, vol="Garch", p=1, q=1, dist="t", mean="constant")
```

**Justification:**

- GARCH(1,1) is the workhorse of volatility modeling
- Student-t distribution accounts for fat tails
- Constant mean is appropriate for daily returns

**Protocol:**

1. Fit on training data only (pre-split date)
2. Generate rolling or fixed forecasts on test set
3. No refitting on test data

**Expected Outputs:**

| Artifact | Purpose |
|----------|---------|
| Model summary table | Parameter estimates, standard errors |
| Forecast time series | Comparison baseline |
| Residual diagnostics | Model adequacy check |

**Explicitly Excluded:**

- Neural network comparisons (separate notebook)
- Hyperparameter search (GARCH is well-specified)

**Why This Exists:**
> **You cannot claim deep learning "works" without a credible baseline.** GARCH is the minimum viable benchmark. Beating naive persistence is trivial; beating GARCH is meaningful.

**Risks Mitigated:**

- Strawman comparison (weak baseline inflates perceived performance)
- Ignoring 30+ years of volatility research

### **Notebook 06: Deep Learning Models (GRU/LSTM)**

**Purpose:** Implement neural network volatility forecasters with proper training discipline.

**Architecture Documented:**

```
Input: (batch, lookback=20, features)
  → GRU(64, tanh) 
  → Dropout(0.3)
  → Dense(32, relu)
  → Dense(1, linear)
```

**Training Protocol:**

| Component | Choice | Rationale |
|-----------|--------|-----------|
| Scaler | StandardScaler | Preserve relative magnitudes |
| Loss | MSE | Consistent with literature |
| Callbacks | EarlyStopping(15), ReduceLR | Prevent overfitting |
| Validation | Held-out test set | Strict temporal split |

**Critical Design Decision:**
> **No shuffle in time series.** Data is split temporally, not randomly. Shuffling would cause **catastrophic leakage**.

**Expected Outputs:**

| Artifact | Purpose |
|----------|---------|
| `gru_model.keras` | Reproducibility |
| Training curves (loss) | Convergence verification |
| Prediction time series | Evaluation input |

**Explicitly Excluded:**

- Final evaluation metrics (next notebook)
- Hyperparameter search results (appendix)

**Why This Exists:**
> Deep learning notebooks become unreadable when training, evaluation, and interpretation are mixed. **Single responsibility**: train the model, save artifacts, stop.

**Risks Mitigated:**

- Training/test leakage through shuffling
- Overfitting through excessive tuning on test set
- Non-reproducibility from missing artifacts

### **Notebook 07: Evaluation & Comparative Analysis**

**Purpose:** Rigorous out-of-sample evaluation with statistical validity.

**Evaluation Protocol:**

```
Models Evaluated:
├── Naive Baseline (RV_t = RV_{t-1})
├── GARCH(1,1)
└── GRU

Metrics:
├── MSE  → Penalizes large errors
├── MAE  → Robust to outliers  
├── R²   → Variance explained
└── Q-like (QLIKE) → Asymmetric loss, standard in volatility literature
```

**QLIKE Definition:**
$$Q_{like} = \frac{1}{T}\sum_{t=1}^{T}\left(\frac{\sigma_t^2}{\hat{\sigma}_t^2} - \ln\frac{\sigma_t^2}{\hat{\sigma}_t^2} - 1\right)$$

> QLIKE is preferred for volatility because it penalizes **underestimation more than overestimation**—appropriate for risk management.

**Statistical Tests (if sample permits):**

- Diebold-Mariano test for forecast comparison
- Model Confidence Set (Hansen et al.)

**Expected Outputs:**

| Artifact | Purpose |
|----------|---------|
| Metric comparison table | Primary result |
| Forecast overlay plot | Visual comparison |
| Residual analysis | Systematic errors |
| Error distribution by regime | Failure mode identification |

**Why This Exists:**
> **Evaluation is confirmatory, not exploratory.** This notebook answers the research question. All decisions are frozen; only metrics are computed.

**Risks Mitigated:**

- Cherry-picking metrics
- Overfitting to test set through iteration
- Missing statistical significance assessment

## 4. Section-Level Justifications

### Why Problem Framing Exists

> Projects fail when the question is ambiguous. "Predict volatility" is not a research question. "Can GRU outperform GARCH(1,1) on 1-day-ahead S&P 500 realized volatility forecasting over 2020-2021?" is testable and falsifiable.

**Risks Mitigated:**

- Scope creep
- Moving goalposts during review

---

### Why Data Provenance Exists

> In finance, data errors are catastrophic. A single incorrect timestamp can cause look-ahead bias. A missing day can break train/test integrity.

**Checklist:**

- [ ] Data source documented
- [ ] Download date recorded
- [ ] Known issues catalogued
- [ ] Cleaning steps logged

---

### Why Benchmarking Precedes Deep Learning

> Deep learning is not automatically superior. GARCH has 40 years of refinement. If GRU cannot beat GARCH on your data, the problem is likely:
>
> 1. Insufficient data
> 2. Inappropriate architecture
> 3. The task is too noisy for any model

---

### Why Separate Train/Validation/Test

| Set | Purpose | Access During Development |
|-----|---------|---------------------------|
| Train | Fit parameters | ✅ Unlimited |
| Validation | Tune hyperparameters | ✅ Limited |
| Test | Final evaluation | ❌ Once only |

> **Test set contamination** is the #1 cause of unreproducible results in ML papers. Strict discipline is required.
